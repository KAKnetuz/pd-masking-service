# Модуль безопасности персональных данных для LLM

Сервис встраивается в цепочку «система-потребитель → LLM»: находит персональные данные
в запросе, маскирует их, а затем восстанавливает исходные значения (демаскирование),
в том числе в ответе LLM.

## Возможности

- **23 типа ПД**: ФИО, дата и место рождения, паспорт (серия/номер, орган, код подразделения,
  дата выдачи), гражданство, водительское удостоверение, адрес по компонентам, email, телефон,
  ИНН, карта (номер, CVV, PIN, держатель, срок действия), а также СНИЛС, загранпаспорт,
  военный билет, свидетельство о рождении.
- **Контекст вместо шаблонов**: «Александр Пушкин», имена в кавычках, улицы имени, адреса отделений
  банка, ИНН организаций не маскируются; дата без контекста маскируется только рядом с ПД человека.
- **Измеренное качество**: на независимой отложенной выборке precision 99,2%, recall 97,3%;
  на рабочей выборке входных текстов проверки precision 98,9%, recall 96,4% — см. «Качество распознавания».
- **Вариации написания (ТЗ 4.2)**: любой регистр (в т.ч. «иВаН» и КАПС), любой разделитель между меткой
  и значением (`:`, `=`, `—`, скобки, кавычки), служебные слова между ними («ПИН второй карты: 5678»,
  «ИНН клиента 771234567859»), метка после значения («код 258 неверно введён CVV»), пробелы подряд,
  даты `дд.мм.гггг` / `мм.дд.гггг` / `гггг.дд.мм` / `15/03` / «12 марта 1990» / прописью,
  «серия 4509 номер 123456» в любом порядке, номера группами цифр, контрольные суммы (Луна, ИНН, СНИЛС).
- **Стратегии маски**: инициалы, частичная (`45** ****56`), полная, email, токены, метки, синтетика.
- **Настройка по системам** (`config/systems.yaml`): доступ, типы ПД, демаскирование, вид маски,
  правила комбинаций (PIN маскируется только вместе с номером карты).
- **Безопасность**: соответствия хранятся зашифрованными (AES-256-GCM) с TTL, в логах и метриках нет ПД.
- **Надёжность**: идемпотентность по `payload_id`, 429 + `Retry-After` при перегрузке,
  резервное хранилище при отказе Redis.

## Архитектура

```
Потребитель → POST /process → лимит (429) → Processor → DetectionEngine → Masker → MappingStore (Redis ⇄ Memory)
Потребитель → POST /chat → ChatProxy: поиск ПД → маскирование метками → проверка на утечку (422) → LLM (AlfaGen) → демаскирование ответа → Потребитель
```

Логика `/process` (коррелируется по `payload_id`):

| Состояние | Входной payload | Ответ |
|---|---|---|
| нового id нет | исходный текст | маска, соответствие сохраняется |
| id есть | наша маска | исходный текст (демаскирование) |
| id есть | исходный текст | та же маска (ретрай) |
| id есть | текст с нашими масками (ответ LLM) | восстановление по фрагментам |

## Запуск

```bash
cp .env.example .env            # задать ENCRYPTION_KEY и TOKEN_SECRET
docker compose up -d --build    # api на порту 80 + redis
curl -X POST http://localhost/process -H "Content-Type: application/json" \
  -d '{"payload":"Клиент Иванов Иван Иванович, паспорт 4509 123456","payload_id":"demo-1"}'
# {"result":"Клиент ****** **** ********, паспорт **** ******"}
```

Локально без Docker: `pip install -r requirements-dev.txt && uvicorn app.main:app` (хранилище в памяти).

## Настройка систем (инструкция)

1. Новая система — блок в `systems` файла `config/systems.yaml` с уникальным ID; она передаёт его в заголовке `X-System-Id`.
2. `enabled: false` закрывает системе доступ (ответ 403).
3. `pd_types` — список типов ПД для поиска и маскирования (`all` — все типы).
4. `unmask` разрешает или запрещает демаскирование, `masking` задаёт вид маски по типам.
5. `require_combination` включает маскирование типа только вместе с другим; после правки перезапустите сервис.

Запросы без заголовка обслуживаются системой `default_system`.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/process` | `{payload, payload_id}` → `{result}` |
| GET | `/health` | процесс жив |
| GET | `/ready` | состояние хранилища (`ok` / `degraded`) |
| GET | `/metrics` | метрики Prometheus |
| GET | `/docs` | OpenAPI |

Ошибки: `400` некорректный запрос (без эха данных), `403` система не допущена / демаскирование
запрещено, `413` слишком большой payload, `429` перегрузка (`Retry-After: 1`), `500` внутренняя ошибка.

## Эталон маскирования

Формат маски выбран командой (эталонная маска организаторами не задаётся, оценивается качество скрытия и точность границ фрагмента). Вид маски для каждого типа задаётся в `config/systems.yaml` и может отличаться по системам-потребителям.

По умолчанию значение скрывается полностью: каждая буква и цифра заменяется на *, разделители внутри значения (пробел, точка, дефис) сохраняются. Длина и позиции знаков совпадают с оригиналом. Частичная маска (например, последние 4 цифры карты) доступна как настройка strategy: partial в config/systems.yaml.

**Правило границ фрагмента (одно для всех типов):**
- во фрагмент входит только значение персональных данных;
- служебные слова и сокращения остаются открытыми: «серия», «номер», «№», «тел.», «ИНН», «CVV», «пин-код», «г.», «ул.», «д.», «кв.», «года», «г.р.»;
- пробелы и знаки препинания по краям во фрагмент не входят;
- разделители внутри значения (пробел, дефис, точка) сохраняются — маска повторяет форму значения;
- составное значение (паспорт, водительское удостоверение) может состоять из нескольких частей, слова между частями не маскируются;
- адрес маскируется по компонентам: индекс, страна, город, улица, дом, квартира.

**Эталон по 17 категориям (система `default`):**

**Не являются персональными данными клиента и не маскируются:** известные люди («Александр Пушкин написал…»), адреса отделений банка.

**Устойчивость к вариантам написания:** регистр не влияет на распознавание; даты распознаются в форматах `дд.мм.гггг`, `мм.дд.гггг`, `гггг.дд.мм`, `дд/мм`, текстом («12 марта 1990 года») и прописью; поддерживаются разделяющие слова («серия … номер …», «серии … № …»), любой разделитель между меткой и значением и служебные слова между ними. Покрытие измеряется матрицей вариантов (раздел «Качество распознавания»).

**Как проверяется:** 30 эталонных примеров лежат в `tests/fixtures/span_reference.yaml`. Тесты `tests/test_span_reference.py` проверяют точные границы фрагментов, восстановление исходного текста и отсутствие открытых фрагментов в маске. Отчёт по примерам: `python -m scripts.span_audit` (создаёт `span_audit_report.txt`).

## Качество распознавания

Платформа проверки показывает только результат анализа кода, точность маскирования участникам
не видна. Поэтому точность измерена отдельно, а изменения принимались только по измерениям.

### Три выборки и их роли

| Выборка | Откуда | Роль |
|---|---|---|
| **Рабочая**, 446 текстов | входные тексты одного прогона проверки, размечены вручную по ТЗ (431 текст с ПД, 666 значений, 15 ловушек) | поиск ошибок; цифры на ней — **оценка сверху**, правила уточнялись по ней |
| **Отложенная 1**, 150 текстов | сгенерированы LLM после фиксации кода, размечены генератором, разметка проверена вручную | независимая оценка версии `e4f7218`; затем по ней исправлены адреса, и она перешла в рабочие |
| **Отложенная 2**, 80 текстов | сгенерированы после фиксации финальной версии | **независимая оценка финальной версии** `961f766` |

Тексты выборок в репозиторий и логи не попадают (обращались с ними как с ПД, хранятся отдельно).
Рабочая выборка собрана на отдельном диагностическом стенде; код сбора в сдаваемую версию не входит.

### Результаты

| Выборка | Версия | Precision | Recall | Recall по символам | Ловушки с находкой |
|---|---|---|---|---|---|
| Рабочая (446) | до правок → `961f766` | 96,0% → **98,9%** | 79,3% → **96,4%** | 80,9% → **98,1%** | 5 → 3 из 15 |
| Отложенная 1 (150) | до правок → `e4f7218` | 99,1% → 98,7% | 80,2% → 83,6% | 88,7% → 92,0% | 2 → 3 из 30 |
| **Отложенная 2 (80)** | до правок → **`961f766`** | 98,8% → **99,2%** | 96,2% → **97,3%** | 96,3% → **98,5%** | 3 → 2 из 16 |

**Что показала отложенная выборка 1.** На новых данных все типы ПД, кроме адреса, распознавались на 100%,
а адрес — 0 из 40: генератор писал адреса без «г.», «ул.», «д.» («адрес: Тверь, Лесная, 7, 15»), и эта
слабость была в сервисе с самого начала (до правок — тоже 0 из 40). Исправление — общее правило для адреса
после метки; проверено на отложенной выборке 2, которую код до этого не видел.

**Оговорки.** Генератор отложенной выборки 2 частично нарушил ограничения (например, один номер паспорта
повторяется в нескольких текстах), поэтому её разнообразие ниже задуманного. Она оказалась и «лёгкой»:
версия до правок уже даёт на ней 96,2%, так что главный аргумент — абсолютная цифра на новых данных,
а не прирост.

### Метрики и инструменты

- `scripts/eval_gold.py` — precision, recall по значениям, recall и «лишние символы» по символам, ловушки;
  находки получаются тем же путём, что в `POST /process`; `--repo` сравнивает две версии кода.
- `scripts/format_matrix.py` — синтетическая матрица: 19 типов ПД × 7 осей вариативности ТЗ 4.2
  и 25 ловушек; с выборками не пересекается.
- `scripts/check_leakage.py` — есть ли тексты выборки в файлах репозитория (целиком и фрагментами
  по 40 символов).
- **Проверка на платформе.** По рабочей выборке предсказана доля запросов, где ничего не найдено (4,0%);
  в логах следующего прогона проверки — 5 034 из 125 187 маскирований = 4,0%; для финальной версии —
  5 034 из 125 190 = 4,0%.

| Матрица вариантов (синтетика) | До | После |
|---|---|---|
| A. Регистр | 96% | 100% |
| B. Пробелы, неразрывный пробел, табуляция | 91% | 98% |
| C. Разделитель метка → значение | 70% | 93% |
| D. Служебные слова между меткой и значением | 64% | 88% |
| E. Форматы дат | 81% | 100% |
| F. Запись номеров | 88% | 94% |
| G. Положение в предложении | 95% | 100% |
| Ловушки с находкой | 2 из 25 | 0 из 25 |

### Правила выведены из ТЗ, а не из выборки

| Правило | Пункт ТЗ |
|---|---|
| Метки и значения в любом регистре; слова КАПСОМ не считаются признаком имени | 4.1 «Идентификация не должна зависеть от регистра», 4.2 «регистр» |
| Любой разделитель метка → значение (`:`, `=`, `—`, скобки, кавычки), служебные слова между ними, метка после значения | 4.2 «разделяющие слова — "серия хххх номер хххххх"» |
| Даты `дд/мм`, `дд мм`, месяц сокращением, дата прописью | 4.2 «разное расположение года, месяца и даты», «написание даты текстом» |
| Номера группами цифр и через дефис, пробелы подряд | 4.2 «учесть разные вариации написания» |
| Орган выдачи по названию (ОВД, УФМС, «отдел полиции») и после метки | 4.1 «Орган, выдавший паспорт» |
| ФИО после метки роли, слитное ФИО, латиница, границы с инициалами и отчеством | 4.1 «ФИО», «Имя держателя карты» |
| Адрес по компонентам, в т.ч. без «г.», «ул.», «д.» после метки | 4.1 «Адрес (в т.ч. отдельно: страна, индекс, город, улица, дом, квартира)» |
| ИНН организации, адрес офиса банка, известные люди не маскируются | 4.1 «…упоминание поэта Александра Пушкина не является ПД, как и адрес отделения Банка» |

## Демо-прокси с LLM

Схема одной строкой: система-потребитель → POST /chat → поиск ПД → маскирование метками → проверка на утечку → LLM (AlfaGen) → демаскирование ответа → система-потребитель.

**Зачем метки `[ТИП_xxxxxx]`:** модель понимает тип данных и сохраняет смысл запроса, а метка однозначно возвращается к оригиналу.

**Защита от утечки:** замаскированный текст повторно проверяется; если найдены ПД — ответ 422, запрос в LLM не отправляется.

**Соответствие меток и оригиналов** хранится только в памяти на время запроса.

**Пример запроса для жюри:**
```bash
curl -s -X POST http://51.250.4.227/chat -H "Content-Type: application/json" -H "X-System-Id: llm-demo" -d '{"message":"Клиент Иванов Иван Иванович, телефон +7 916 123-45-67, спрашивает, когда спишется платёж по карте 2200 1234 5678 9019. Составь короткий вежливый ответ клиенту с обращением по имени и отчеству."}'
```

**Поля ответа:**
- `sent_to_llm` — что ушло в LLM (замаскированный текст);
- `llm_answer` — что ответила LLM;
- `answer` — ответ потребителю после демаскирования;
- `pd_types` — найденные типы ПД и их количество.

**Ошибки:** `403` — система не указана, не допущена или ей запрещено демаскирование; `422` — сработала защита от утечки; `503` — LLM недоступна.

**Настройка:** `LLM_PROVIDER=alfagen|stub`, `LLM_API_KEY` (только в `.env` на сервере, не в репозитории), `LLM_BASE_URL`, `LLM_MODEL`, `LLM_TIMEOUT_SECONDS`, `LLM_CA_BUNDLE`.

**Ограничение:** если модель изменит метку в ответе (например, уберёт скобки), этот фрагмент не восстановится.

## Нагрузочное тестирование

Профиль проверяющей системы (со слов организаторов):

- до 200 одновременных соединений;
- каждое соединение работает синхронно: `POST /process` (маскирование) → ждёт ответ →
  `POST /process` с тем же `payload_id` и полученной маской (демаскирование);
- нагрузка с разгоном, в среднем ~330 RPS, пики до 1000;
- тексты разного размера;
- `429` не считается ошибкой: проверяющая система ждёт `Retry-After` и повторяет до 2 раз;
- смотрят среднее, p50, p95, p99.

Сценарий выбирается переменной окружения `SCENARIO`:

- `checker` (по умолчанию) — `ramping-vus`: 0→50 VU за 30s, 50→200 за 60s, держать 200 VU 120s, 200→0 за 30s;
- `rps1000` — `constant-arrival-rate`, 500 итераций/с (итерация = 2 запроса = 1000 RPS), 60s;
- `rps2000` — то же, 1000 итераций/с (2000 RPS).

Одна итерация: уникальный `payload_id`, случайный текст (60% — короткие фразы, 35% — сложное
предложение, 5% — длинный текст ~20 000 символов), маскирование → проверка 200, демаскирование →
проверка, что `result` равен исходному тексту. При `429` — ожидание `Retry-After` и повтор (до 2 раз).

Команды запуска:

```bash
k6 run load/k6_process.js
k6 run -e SCENARIO=rps1000 load/k6_process.js
k6 run -e SCENARIO=rps2000 load/k6_process.js
```

`BASE_URL` берётся из переменной окружения (по умолчанию `http://51.250.4.227`). Результаты
сохраняются в `load/results/summary-<SCENARIO>.json`.

### Условия замеров
- Сервер: ВМ Yandex Cloud, 8 vCPU (гарантированная доля 100%), 16 ГБ RAM, Ubuntu 24.04.
- Сервис: docker compose — 8 воркеров uvicorn + Redis 7 (хранилище соответствий, шифрование AES-256-GCM).
- Настройки: MAX_INFLIGHT=64 на воркер, REDIS_TIMEOUT_SECONDS=2.0, REDIS_MAX_CONNECTIONS=128.

- Одна итерация = пара запросов с одним payload_id: маскирование → демаскирование полученной маской. Проверяется, что маска изменила текст с ПД и что демаскирование вернуло исходный текст символ в символ.

## Отказоустойчивость

- **Таймаут Redis** → один повтор, затем `503` с `Retry-After` (без тихой подмены ответа).
- **Redis недоступен** → запросы обслуживает хранилище в памяти, `/ready` показывает `degraded`.
- **Перегрузка** → `429` с `Retry-After`, а не рост очереди и таймауты.
- **Ретраи** проверяющей системы безопасны: повтор маскирования возвращает ту же маску.
- **Неверный конфиг** → сервис не стартует (ошибка видна сразу, а не в проде).
- **В `/chat`:** LLM недоступна → `503`; сработала защита от утечки → `422`, запрос в LLM не отправляется.
- **Redis хранит соответствия только в памяти** (лимит 4 ГБ, время жизни записи MAPPING_TTL_SECONDS, по умолчанию 900 с); при нехватке памяти вытесняются записи с ближайшим сроком истечения.

## Ограничения и план развития

- Распознавание построено на правилах и словарях (без ML) ради latency; редкие фамилии без
  типичных суффиксов распознаются только при контексте («клиент», «ФИО:», метка роли) или рядом с
  именем/отчеством.
- Оставшиеся ошибки на выборках: месяц, записанный шаблоном («15 Mмм 1990»); дата выдачи без слова «дата»
  («паспорт выдан 15 03»); место рождения из повествования («родилась весной. В Москве…»);
  «область»/«край» после места рождения остаются открытыми; фамилии через «/» без имени; отдельные
  нестандартные записи адреса и органа выдачи.
- ФИО в кавычках («Евгений Онегин») намеренно не маскируется как название; дата договора или визита
  маскируется, если в том же тексте есть ПД человека.
- Длинные тексты обрабатываются заметно дольше: ~100 мс на поиск ПД в тексте 20 000 символов
  (оценка для 100 000 токенов — около 2–3 с, укладывается в таймаут 10 с).
- Основное время на длинных текстах тратят детекторы ФИО и адреса — профиль:
  `python -m scripts.profile_detectors`. Это первый кандидат на оптимизацию.
- Замеры выполнены изнутри ВМ; для внешнего клиента к задержке добавляется сетевое время.
- Если Redis недоступен, сервис переходит на хранилище в памяти воркера (деградация): маскирование
  продолжает работать, но пара маскирование → демаскирование гарантированно восстанавливается
  только в пределах одного воркера.
- Если запись соответствия пропала (перезапуск Redis, истёк TTL), повторный запрос обрабатывается
  как новый текст.

**План развития:**
- ускорение детекторов ФИО и адреса;
- ключи доступа для всех систем;
- NER-модель как второй этап для редких фамилий и мест из повествования;
- регулярный пересчёт `eval_gold` на новых выборках как регрессионный контроль качества;
- горизонтальное масштабирование (несколько экземпляров за балансировщиком с общим Redis).
